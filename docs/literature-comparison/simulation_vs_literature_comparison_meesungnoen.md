# simulation_vs_literature_comparison_meesungnoen.csv

Table of water-radiolysis G-values (time-dependent species yields) for **500 keV electron** irradiation under
`/process/dna/e-SolvationSubType Meesungnoen2002`, comparing this work's Geant4-DNA (`dnachem-min`) simulations
against two published, hand-digitized literature datasets. Generated by
`JupyterLab/PFAS/GEANT4/literature-comparison/meesungnoen_vs_literature.ipynb`, section 4. 1952 rows x 10 columns.

This is the Meesungnoen2002 counterpart of `simulation_vs_literature_comparison.csv` (which uses the
`Ritchie1994` default) — see that file's own `.md` for background. It answers the note added there on
2026-10-13: "this table was not regenerated [under Meesungnoen2002]... re-run the electron batches (and the
notebook) before using it for a like-for-like comparison." Only the **electron** beam is exported here: the
Meesungnoen2002 proton restart (`261013_Farokhi2023_proton_20um_meesungnoen`) has no IRT_syn/SBS pair to put in
two columns the way the electron sets do, so it is covered only by the figures in
`meesungnoen_vs_literature.ipynb`, not by this export.

**Not a drop-in replacement** for `simulation_vs_literature_comparison.csv`: the Meesungnoen2002 electron runs
use track-segment `eLossMin = 50 keV` (10 %), not the `12.5 keV` (2.5 %) of the Ritchie1994 export, because that
is the only Meesungnoen2002 electron track-segment length currently available in `DATA_SIM`. A difference
between the two CSVs can come from the solvation submodel, the eLossMin change, or both — they are not isolated
here.

## Shape

One row per (O2 level, species, time point); one column per source. All sources share the same time axis within
each (O2 level, species): the simulation's own 61 log-spaced recording times (~1 ps to ~1 us, 10 points/decade,
identical for every run used here). Literature curves, which are hand-digitized at irregular time points, are
**log-time-linearly interpolated onto this same 61-point grid** so every source column can be read off the same
`time_s` values with no further resampling needed.

```
particle  beam_energy_keV  O2_pct  O2_uM  species  time_s  IRT_syn  SBS  Farokhi  Boscolo
```

1952 rows = 61 time points x 4 O2 levels (0 / 2.5 / 5 / 21 %) x 8 species.

## Columns

| Column | Meaning |
|---|---|
| `particle` | Always `e-` (electron) — constant, included for self-description. |
| `beam_energy_keV` | Always `500.0`. |
| `O2_pct` | O2 level as the papers label it: 0, 2.5, 5, or 21 %. |
| `O2_uM` | Dissolved O2 concentration in uM matching `O2_pct` (Henry's-law value at 37 C; 0 / 26.0 / 51.9 / 218 uM). This is the actual O2 content used by the simulation's scavenger reactions; literature rows reuse the value for the matching `O2_pct`. |
| `species` | Column-safe species tag, see below. |
| `time_s` | Time since the primary event, in seconds. The same 61 values repeat for every (O2_pct, species) pair. |
| `IRT_syn` | G-value (molecules / 100 eV) from this work, IRT_syn (independent-reaction-times) time-step model, Meesungnoen2002 solvation. Never `NaN`. |
| `SBS` | G-value from this work, SBS (step-by-step) time-step model, Meesungnoen2002 solvation. Never `NaN`. |
| `Farokhi` | G-value from Farokhi et al. 2023, hand-digitized. `NaN` where neither digitized nor physically derivable — see below. |
| `Boscolo` | G-value from Boscolo et al. 2020, hand-digitized. Same `NaN` policy as `Farokhi`. |

## Species tags (`species` column)

Column-safe tags, not the raw simulation species names:

| Tag | Species | Literature coverage |
|---|---|---|
| `e_aq` | hydrated electron, e-_aq | `Farokhi`/`Boscolo` digitized (Farokhi missing a few grid points/one O2 level — see below) |
| `H` | hydrogen atom | `Farokhi`/`Boscolo` digitized (Farokhi has no curve at all at 21 % O2 — `NaN` throughout for that O2 level) |
| `HO2` | hydroperoxyl radical (oxygen-related, O2 scavenging product) | `Farokhi`/`Boscolo` digitized; both are 0 at 0 % O2 (physically required, not just undigitized) |
| `O2` | superoxide, O2.- (oxygen-related, O2 scavenging product; **not** molecular O2 — dissolved O2 is a scavenger input, not a scored species) | Same as `HO2` |
| `OH` | hydroxyl radical | `Farokhi`/`Boscolo` = `NaN` throughout — **not digitized for the electron figures by either paper** |
| `H3Op` | H3O+ (`p` stands in for `+`) | `Farokhi`/`Boscolo` = `NaN` throughout |
| `H2` | molecular hydrogen | `Farokhi`/`Boscolo` = `NaN` throughout |
| `H2O2` | hydrogen peroxide | `Farokhi`/`Boscolo` = `NaN` throughout |

Only `e_aq`, `H`, `HO2`, `O2` are the 4 species either paper digitized for their electron-beam figures; the
simulation scores all 8. **`NaN` means "no information", not "zero"** — see the policy below.

## NaN / zero policy for `Farokhi` and `Boscolo` (read this before aggregating)

`IRT_syn`/`SBS` are always real numbers (0 included) — a simulation `(species, time)` pair absent from the raw
ntuple means **true G = 0**, which is how the simulation's own output stage already writes it.

`Farokhi`/`Boscolo` are `0` only in two specific, physically-justified situations, and `NaN` everywhere else we
simply don't have digitized data:

| Situation | Value used | Why |
|---|---|---|
| Species never digitized for this paper's electron figure (`OH`, `H3Op`, `H2`, `H2O2`) | `NaN` | No information at all — reporting 0 would be a false claim about the paper. |
| A specific (species, O2 level) curve is missing even though the species is digitized elsewhere (Farokhi `H` at 21 % O2) | `NaN` | Same reason — H is certainly produced at 21 % O2, we just don't have Farokhi's curve for it. |
| Grid time outside a digitized curve's own time range (e.g. before its first or after its last digitized point) | `NaN` | No assumption about the curve's shape outside what was actually digitized. |
| `HO2` or `O2` (superoxide) specifically at 0 % O2, curve missing or not | `0` | Physically required: no dissolved O2 means no scavenging pathway can produce either species, independent of whether the paper bothered to plot a trivial flat zero. |
| Hand-digitized `HO2`/`O2` points that read slightly negative near 0 % O2 (reading noise on a curve hugging zero) | floored to `0` | G-values cannot be physically negative. |

**Practical implication**: `.mean()`, `.corr()`, NMAE, etc. against `Farokhi`/`Boscolo` must either `.dropna()`
first or use a `NaN`-aware reducer — a plain sum/mean treating `NaN` as 0 would silently bias results toward
"simulation matches zero", which is wrong. Pandas's default reducers (`mean`, `std`, correlation) already skip
`NaN` by default, but anything indexed/joined manually should check for this explicitly.
